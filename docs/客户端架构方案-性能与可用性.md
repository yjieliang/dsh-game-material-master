# 客户端架构方案 v2 · 性能与可用性优先

> 定位：这是**架构地基**方案，不是「怎么把 8,340 行搬出去」的搬家单。
> 旧计划（`docs/客户端拆分-计划.md`）保留为**迁移步骤参考**；两者冲突时以本文为准。
> 已落地：`src/client/ui.ts`（commit `dc4304f`）在新方案里归入 `platform/ui`。

## 1. 为什么重写方案

用户目标已经从「减少 client.ts 行数」升级为：**性能优先、可用性优先，为未来规模增长打地基**。
但插件有个硬约束必须先摆到桌面：

**产物体积与拆分无关。** 浏览器拿到的永远是 esbuild 内联出来的**单文件经典脚本**（无模块系统），
拆文件**不减少一个字节**。所以「性能」只能从这几处拿：

1. 少做无谓工作（惰性挂载、精确订阅、去重、缓存）
2. 少让 React 重渲染（现在每次轮询都可能重渲染整棵模块子树）
3. 少发重复请求（现在 4 个模块各自 2.5s 轮询，互不知道对方）
4. 失败时快速降级而不是拖死整页（现在没有错误边界）

「可用性」同理：不是部署冗余，而是**故障隔离 + 自愈 + 不丢状态 + 不重复花钱**。

### 2.2 结构性风险（对应未来增长）

| # | 风险 | 现状证据 | 放大后的后果 |
|---|---|---|---|
| R1 | **轮询 → 整树重渲染** | 0 个 `useSyncExternalStore`；任务态是组件 `useState`；2500ms 轮询 4 处 | 模块从 8 个涨到 20 个、单模块更复杂时，主线程被周期性挤占，地图/骨骼这类 canvas 编辑器掉帧 |

| R6 | **定时器/监听泄漏** | 39 timers + 41 listeners 散在各组件 `useEffect` | 切模块/重载后残留回调持续请求，越用越慢 |
| R7 | **静默丢键** | 188 个方法靠 zod schema 白名单（历史上 4 起事故） | 方法数继续涨时，漏写 schema 的概率线性上升 |
| R8 | **启动即全量构造** | 8 个模块组件在 `apply()` 时全部 `createXxxModule` 构造；`StudioPanel` 一次收 8 个组件 | 模块数翻倍后启动变慢、内存常驻变大 |

### 2.4b P10 定时器收编收尾（2026-10-28）

P3b 只搬了工作台与①③②的轮询，剩下的 5 处轮询与 6 类防抖 / 延时还在用裸定时器。
P10 按「语义」分两类处理，非 platform 裸定时器从 **16 → 0**（`verify-arch` 棘轮上限同步 16 → 0）：

| 类别 | 原实现 | 现在 | 说明 |
|---|---|---|---|
| iso 作业中刷新（1.5s） | `setInterval` | `scheduler.watch("iso:<id>:busy")` | 去重 / 退避 / 隐藏暂停 |
| map 作业中刷新（1.5s） | `setInterval` | `scheduler.watch("map:<id>:busy")` | 同上 |
| music 任务轮询（4s） | `window.setInterval` | `scheduler.watch("music:<jobId>")` | 依赖里**不含** `updatedAt` |
| sfx 任务轮询（2.5s） | `window.setInterval` | `scheduler.watch("sfx:<jobId>")` | 同上 |
| rig 任务轮询（2.5s） | `setInterval` | `scheduler.watch("rig:<jobId>")` | busy 或沉降窗期间 |
| iso 计划查询防抖（20/60ms）、iso 动画钟（90ms） | `setTimeout` / `setInterval` | `lifecycle.onceTimer` / `repeatTimer` | 动画钟是纯表现层时钟，不进调度器 |
| map 计划查询防抖（32ms）、预览节流（80ms） | `setTimeout` | `lifecycle.onceTimer` | 语义不变（仍随 effect cleanup 取消） |
| sequence 提交后补刷阶梯（1.2/3/5.5/9s） | 4 × `setTimeout` | `lifecycle.onceTimer` | 一次性阶梯，不是周期轮询 |
| ui 待处理提示保持（700ms）、复制按钮复位（1.6s） | `setTimeout` | `lifecycle.onceTimer` | 纯 UI 延时 |

两个新帮手在 `platform/lifecycle.ts`：`onceTimer(fn, ms)` / `repeatTimer(fn, ms)` 都返回取消函数
（在 effect cleanup 里调，替代 `clearTimeout` / `clearInterval`）。**会发请求的周期轮询仍然只能走
`scheduler.watch`** —— 调度器才有去重、退避、页面隐藏暂停与并发上限。

踩坑记录：`verify-map-client` 用「可取消定时器队列 + 手动 pump」模拟真机时序，busy 轮询改走
`scheduler.watch` 后它拿不到那个 1.5s 回调 —— 现在 harness 把 `window.__GMM_SCHEDULER__.watch`
接到同一个 `intervals` 队列（`tickIntervals()` 仍等价于「又过了 1.5s」），并新增「登记项 key /
间隔 / 非 immediate」与「时钟一到真的重读项目」两条断言。这类夹具改动要用 `withFreshHooks`
的临时 Hook 存储渲染，否则会把正在测的面板状态清掉（本机实测：直接 remount 后拖拽 / 撤销全红）。

**状态归属的发现**：sprite 四阶段自己不持有数据 —— 项目快照由 StudioPanel 持有并向下传（project prop），
所以「把状态搬进 feature store」必须等 P6 的 shell/panel 切片，否则只是把状态换个地方再传一遍。
P3b 因此只做调度器收编，store 迁移并入 P6。

### 2.7 轮询的「没变就不重渲染」（2026-10-28）

> 订阅粒度问题已在 §2.8 解决；本节只讲「内容签名没变就跳过 setState」。

工作台每 2.5 秒拉一次 getProject / getSequenceJob 等。绝大多数时刻宿主那边的数据一个字节没变，
但 setState 拿到的是新对象引用 —— React 只能整棵子树重渲染一遍。

现在 loadProject 先算签名：

    const next = await api.getProject(id);
    const previous = loadedPrompts.current;
    const signature = JSON.stringify(next ?? null);
    const forceUpdate = options.resetDrafts === true;
    if (!forceUpdate && previous.projectId === id && signature === previous.signature) return;

三个条件缺一不可：换项目（projectId 变了）必须刷新、用户点「重置为默认」必须刷新、
其余情况内容没变就直接返回。真机验证：控制台里 __GMM_PERF__.renderCount("StudioPanel")
在任务跑着但数据没变时应保持不变。

注意这一步**不改变订阅粒度**：数据一变仍是整棵子树重渲染（state 还在面板里）。
要做到「一次轮询只重渲染 ≤3 个组件」，需要把 project 拆成按模块的选择器订阅 ——
这一步已在 §2.8 完成。

### 2.8 P9 store 选择器订阅：轮询重渲染实测（2026-10-28）

§2.7 的「签名没变就跳过」只挡住了「数据一个字节没变」的轮询；数据真的变了（例如某个方向
从 running 变 ready）时，state 还在面板里，React 仍然要重渲染整棵模块子树。这一步把状态搬进
`platform/store`，组件改成按 selector 精确订阅，把「一次轮询重渲染的组件数」压到 3 个以内。

**测量方法与数据**（可复跑：`node scripts/perf-poll.mjs scripts/tmp/client-before-121bf0d.js lib/client.js --labels=改前,改后`）

- harness：`scripts/perf-poll.mjs` 用假 React 实现一个迷你渲染器（useState 的 setter 真的触发重渲染、
  useRef 跨渲染保持、useEffect/useCallback/useMemo、useSyncExternalStore 订阅 + 快照比较、
  memo 自定义比较、Component 类组件与错误边界），配假时钟 + 捕获式 `setInterval`，然后**手动触发一次
  `scheduler` tick**（等价于一次 2.5 秒轮询到点）；
- 两个 bundle 用同一份 harness 跑：改前 = HEAD `121bf0d` 的 `lib/client.js` 副本
  （1,117,614 B，sha256 `311ba3a3…`），改后 = 本次 `lib/client.js`；
- 场景 `changed`：有任务在跑（jobs 挂着 `images:all`）时轮询回来，差异只有 `images.upLeft`
  running → ready（仍是 busy，所以轮询不会停）；
- 场景 `idle`：同一份数据连续轮询 3 次，回包 1 字节没变；
- 数字都是**组件函数调用次数**（假渲染器在每次调用组件时记一笔，与真 React「一次渲染 = 一次组件函数调用」同口径）。

| 指标（changed 场景一次轮询） | 改前 | 改后 |
|---|---|---|
| **产品组件重渲染数**（验收口径：有 `markRender` 埋点的订阅单元） | 1 个（`StudioPanel`，一次重画整树） | **3 个**：`SpriteImageDirectStage` / `SpriteLog` / `SpriteSourceCard` |
| `StudioPanel` 重渲染（`__GMM_PERF__.renderCount`） | 1 次 | **0 次** |
| 全部组件函数调用（原始口径，含展示型子组件） | 93 次 / 14 种 | **74 次 / 11 种** |
| idle 场景（3 次轮询）组件调用总数 | 0 | 0（§2.7 已兑现） |
| 挂载一次（一次性成本） | 118 次 / 14 种 | 129 次 / 27 种（拆出订阅壳，多 13 个组件） |

结论：**一次数据有变的轮询，产品组件重渲染 3 个（≤3 达成），面板本身 0 次**；空闲轮询两版都是 0。
原始口径 93 → 74 只降了 20%，是因为改后重画的那 3 块里仍要调用自己的展示型子组件
（71 次调用属于 `Btn` / `Chip` / `MediaBox` 这类原子组件），这是「只重画 3 块中的一块」的固有成本。

**口径说明（为什么「≤3」按产品组件算）**：这里把「组件」定义为**带 `markRender()` 埋点的产品组件**
（`StudioPanel`、`Sprite*` 订阅壳、8 个模块根、设置页），展示型原子组件
（`Btn` / `BusyBtn` / `Chip` / `StatusChip` / `MediaBox` / `SaveLink` / `LoadingOverlay`…）不计入
——它们没有自己的状态，只是父组件的渲染产物；改前改后**同一口径**对比。改前产品口径只有
`StudioPanel` 一个埋点：它重渲染 1 次 = 整棵树重画（原始 93 次调用）；改后是 3 个**独立订阅单元**
各自重画自己那一小块，面板与其余 7 个模块都没有被叫醒。要再往下压原始调用次数，得把整块重画的
展示型子组件也 memo 掉（回调引用的陈旧闭包风险大），不在本轮范围。

**做了什么**

- `platform/store.ts`：`createStore` 增加 `batch(fn)`（一次轮询回包的多处写入合并成一次通知）与
  创建时注入 React（自检桩也能用）；新增 `createStudioStateStore` —— 状态是
  `projects / projectId / project / promptDraft / videoPromptDraft / settingsDraft / promptOpen`，
  草稿写入器用 `sameDraft` 做内容短路（`mergeDrafts` 对对象草稿总是返回新对象，不短路的话
  「参数草稿」会让面板每轮询都重渲染）；`shallowEqual` 供返回数组/小对象的 selector 用。
- 组合根 `shell/bootstrap.ts` 创建**唯一** store，`provideRuntime({ store })` + 注入 composition；
  面板与 8 个 feature 工厂签名统一收 `store`。
- `studio-panel.ts` 拆订阅：面板只订阅 `projectId`（切项目才变）；审核模式条、阶段页签、源图卡、
  阶段主体、运行日志、阶段工具栏、项目列表、顶栏项目操作各自按 selector 订阅自己那段，用字段级
  比较器（`projectFieldsEqual`）挡住无关变化。**轮询开关改成「effect 里订阅 store、不参与渲染」**：
  任务开始/结束（busy 翻转）不再让面板重渲染。
- `features/sprite/index.ts`：四个阶段渲染函数改成自订阅组件 —— `renderImageStage` 只订阅
  `imageMode`，逐方向主体 `ImageDirectStage` 订阅 images/prompts/source/jobs，
  `TurnImageStage` 订阅 turn，`FrameStage` / `renderSheetStage` / `WalkPreview` 各自订阅；

## 3. 设计目标（SLO）

> 数值按「本机桌面浏览器、8 个模块、真实项目数据」定；括号内是当前近似值或未知项。

| 维度 | 指标 | 目标 | 测法 |
|---|---|---|---|
| 启动 | 面板首次可交互 | ≤ 300 ms（当前未测） | 浏览器 `performance.mark` + 宿主侧首包时间 |
| 启动 | 非活动模块不挂载 | 挂载数 = 1（当前未知） | 渲染计数埋点 |
| 渲染 | 一次轮询导致的组件重渲染 | ≤ 3 个（当前可能整树） | 开发态 render counter |
| 渲染 | 编辑态交互帧 | canvas 编辑器 ≥ 50 fps，输入无卡顿 | RAF 采样 + 长任务统计 |
| 网络 | 轮询请求数（8 模块同时挂任务） | ≤ 活跃任务数（当前 4 模块各自跑） | 请求计数器 |
| 网络 | 断网/5xx 自愈 | ≤ 3 次退避内恢复，期间不刷屏报错 | 注入失败中间件 |
| 稳定性 | 单模块渲染异常 | 外壳可用、可切模块、有降级占位 | 故意抛错的 falsy fixture |
| 稳定性 | 30 分钟轮询 | DOM 节点数不增长、rAF/定时器数不增长 | 内存与计数快照 |
| 资金安全 | 付费调用重复提交 | **0**（重试只限只读方法） | 计数断言 + receipt |
| 体积 | `lib/client.js` | ≤ 1.2 MB raw / ≤ 320 KB gzip | 构建脚本预算断言 |

**关键取舍**：为了性能与可用性，可以接受**更多的文件与一层抽象**；不接受在渲染热路径上引入新开销
（例如每帧都走 Context/订阅），也不接受「为了少改代码」而保留整树重渲染。

## 5. 关键机制

### 5.1 精确订阅取代整树刷新（R1）

- `platform/store.ts`：`createStore<T>` 返回 `{ getState, setState, subscribe, batch }`；
  `store.use(selector, isEqual?)` 基于 `React.useSyncExternalStore`（React 在创建 store 时注入，自检桩也能用）。
  **已落地（P9，§2.8）**：面板共享状态由 `createStudioStateStore` 持有，轮询回包走 `batch` 合并通知；
  8 个模块的组件签名统一收 `store`。一次轮询重渲染的**产品组件**从「整棵树」降到 **3 个**（面板 0 次）。
- 轮询结果写进 store，不在组件 `setState`；列表页用 selector 订阅数组引用，卡片用 selector 订阅单条。
  草稿写入器带 `sameDraft` 内容短路：内容没变就不通知（否则 `mergeDrafts` 每次返回新对象，
  「参数草稿」会让面板每轮询都重渲染）。
- 高频路径（`TurnAxis` 播放、地图脏块、走位预览）**不进 React state**：用 `ref` + `requestAnimationFrame`，
  每帧最多画一次；状态变化走 store 但节流为「每帧合并一次」。
- 收益上限：一次轮询重渲染组件数从「整棵模块子树」降到「用到该数据的 1–3 个」（已实测，见 §2.8）。

### 5.2 PollScheduler（R2）

一个集中调度器，取代 10 个散落 `setInterval`：

- **注册**：`scheduler.watch(key, { intervalMs, run, enabled })`，返回取消句柄；组件卸载 / 模块隐藏自动退订。
- **去重**：同一 `key` 只保留一个在飞请求（inflight merge），下一次 tick 发现上次未回就跳过并计「落后」。
- **退避**：失败按 1s → 2s → 4s（上限 = 基础间隔）退避并加 jitter；成功后复位。
- **可见性**：`document.visibilityState === "hidden"` 时全暂停，回到前台立即补一次。
- **并发上限**：默认 3，超出排队；付费类方法永远不排队重试。
- **可观测**：`__GMM_PERF__.polls` 计数（次数/耗时/失败率），开发开关打开。

### 5.3 ApiClient（R3/R4/R7）

- **方法元数据表**：由 `wire.ts` 的 188 个方法生成一侧元数据（读 / 写 / 付费 / 幂等键需求），
  客户端按类执行策略：读 → 可重试（2 次，指数退避）；写 → 不自动重试；付费 → 必须 `confirm` +
  幂等键（`requestId`）+ 本地 receipt 落盘（宿主已有 ToAPIs receipt，推广到全部生成类）。
- **统一执行**：超时（默认 60s，长任务走作业轮询而不是长请求）、`AbortController` 取消、错误归一化
  （`{ code, message, retriable, requestId }`）—— 各处不再各写 `try/catch + msg()`。
- **schema 护栏**：漏写 schema 仍是历史事故源；在自检里增加「新增方法必须有 payload/result 声明」，
  并在客户端元数据表里同源于 `wire.ts`，一处漏了另一处会当场失败。

### 5.4 故障隔离与自愈（R3）

- 每个 feature 的根组件包一层 `<FeatureBoundary module="map">`：捕获渲染/生命周期异常 → 渲染降级卡片
  （「该模块暂时不可用，可切到其它模块 / 重试」），并上报一次（`__GMM_PERF__.errors`）。
- `shell` 再包一层总边界：连外壳都炸时才显示最简降级页（不做白屏）。
- `apply(ctx)` 整个过程 fail-open：任何子服务缺失（locale/sessions/remote）只降级该能力，不阻断挂载。
- 轮询/请求失败只影响对应卡片（局部 error 状态），不冒泡成整页错误。

### 5.5 惰性挂载与虚拟化（R8/R1）

- **模块级**：只有当前页签的模块 `Component` 被挂载；其余保持 descriptor 但**不渲染**。
- **任务级**：作业列表超过 50 条启用窗口化（固定行高、只渲染可视区 ±buffer）；不引第三方库，40 行实现。
- **重组件**：骨骼时间线、地图大图的 `useMemo` 只在依赖变化时算；`React.memo` 按「数据引用 + 版本号」比较。
- **图片**：`loading="lazy"`、`decoding="async"`，避免一次性解码几十张缩略图。

### 5.6 资源登记与生命周期（R6）

- `platform/lifecycle.ts`：`useResources()` 统一登记 timer / RAF / listener / abort，卸载时一次性释放；
  代码里出现裸 `setInterval` 由架构自检拦下（见 5.9）。
- 客户端每次加载都是全新模块图，没有宿主那套 `disposed` 陷阱；但**定时器跨重载不会自动消失**，
  因此必须在卸载时清理（当前有 39 处盲区）。
- 宿主侧同理：`activate*` 复位约定保留，新增任务管理器必须挂到 `ctx.effect` 的 dispose 上。

### 5.7 体积与启动（R8）

- 预算断言：raw ≤ 1.2 MB、gzip ≤ 320 KB（当前 1.05 MB / 284 KB，只剩约 12% 余量）。
- 不做动态 import（宿主没有模块加载器，分片需要宿主支持多脚本注入，列为未来项，不在本版）。
- 启动期不做业务计算：descriptor 注册只放常量；模块构造推迟到首次挂载。

### 5.8 可观测性（性能与可用性都要能告警）

- 开发构建提供 `window.__GMM_PERF__`：`{ polls: {count, ms, failures}, renders: Map<组件,次数>, errors: [] }`。
- 生产构建保留极轻量计数（只统计失败与超时），随错误一起上报给宿主日志。
- 每个 feature 的性能面板可由开关打开（默认关闭，零开销）。

### 5.9 架构适配度自检（fitness functions）

新增 `scripts/verify-arch.mjs`（进 `gate` 核心集），断言：

| # | 断言 |
|---|---|
| 1 | `features/*` 不 import 其它 `features/*` |
| 2 | `platform/*` 不 import `features/*`、`shell/*` |
| 3 | 客户端源码没有裸 `setInterval`/`fetch(`（除 platform 允许的文件） |
| 4 | 每个 feature 有 `descriptor.ts` 且在 registry 注册 |
| 5 | `lib/client.js` 体积在预算内 |
| 6 | 没有新增第三方 import（`verify-tools` 已有，保持） |
| 7 | 每个 feature 根组件被 `FeatureBoundary` 包裹 |

只有**能自动拦住**的规则才算地基；写在文档里靠自觉的规则，一年后必然失效。

## 8. 风险与「明确不做」

**做**：store + 精确订阅、集中调度、错误边界、ApiClient 元数据、架构自检、惰性挂载、虚拟列表。

**不做（及理由）**：

| 不做 | 理由 |
|---|---|
| 引第三方状态库（zustand/redux） | 客户端不许 import 第三方；自写 60 行 store 足够 |
| 动态 import / 分包 | 宿主只注入单脚本；除非宿主支持多 chunk，否则不可行 |
| Web Worker 跑压缩/解码 | 需要额外脚本与宿主路由支持，收益在图片解码，优先级低于渲染问题 |
| 一次性大重构 | 无法定位回归；按 P0–P8 渐进，每步回滚 |
| 在渲染热路径用 Context 传高频数据 | Context 变更会重渲染全部消费方；高频数据走 store selector/ref |

**主要风险**：

1. `useSyncExternalStore` 引入后订阅粒度过粗 → 仍整树刷新。对策：selector 返回原始值 + `Object.is` 比较，卡片级订阅。
2. 调度器成为单点：它自己崩了就全停。对策：调度器内部 try/catch，单任务异常隔离并计数。
3. ApiClient 元数据表与 `wire.ts` 漂移。对策：由 `wire.ts` 派生（同源），漂移即自检失败。
4. 迁移期间新旧两套路径并存（一半轮询在旧 `setInterval`、一半在 scheduler）→ 双倍请求。对策：P3 起每迁一个模块就删掉旧定时器，验收里看请求计数。

## 8.5 已踩的坑（P1 当天）

**platform 的顶层标识符不能用通用名。** 产物是单文件 IIFE：esbuild 会把跨模块重名的顶层标识符
改名为 `xxx2`，而 `verify-client` 里有一批「按产物文本钉住调用点」的契约（例如
`function mergeDrafts(current, previous, next, force)`）。`runtime.ts` 最初用模块级
`let current`，结果 `mergeDrafts` 的参数被改名成 `current2`，**3 条草稿契约当场变红**。
修法：platform 顶层变量一律加前缀（如 `gmmRuntime`），并加了 `verify-arch` 的通用名黑名单检查。
